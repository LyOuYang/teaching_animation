# APCSP：没有总指挥的互联网 (Internet Layered Responsibilities)

> **教学愿景**：用“打开一个网页”的真实消息过程，讲清为什么互联网不需要中央大脑也能工作。
> **核心概念**：`Internet vs Web`、`protocol`、`packet`、`routing`、`fault tolerance`、`bandwidth`、`scalability`、layered responsibilities。
> **适用人群**：AP Computer Science Principles 学生 / 高中信息技术与编程初学者
> **预计时长**：20-25 分钟

---

## 📚 知识点总览

1. `Internet` 是基础网络，`Web` 是运行在其上的一种服务。
2. 数据会被拆成多个 `packet`，方便传输、补发和重组。
3. `protocol` 是共享规则，让独立系统能够协作。
4. `routing` 和 `redundancy` 让网络在局部故障时仍能继续工作。
5. 分层不是背名词，而是划分“谁负责什么”。
6. `bandwidth` 影响一次能流过多少数据，`scalability` 说明系统能否继续扩展。

---

## 🎯 学习目标

- 能区分 `Internet` 与 `World Wide Web`
- 能解释为什么网页请求会被拆成多个 `packet`
- 能用自己的话说明 `protocol` 的作用
- 能解释为什么一条路径断开后数据仍可能送达
- 能理解分层是在划分职责边界，而不是顺序背诵
- 能说出 `bandwidth` 与 `scalability` 为什么和互联网设计有关

---

## ⚠️ 常见误区

- **误区 1**：Web 就是 Internet  
  **纠正**：Web 是 Internet 上的一种服务，不是整个 Internet。

- **误区 2**：互联网有一个中央控制者  
  **纠正**：互联网由很多独立设备和网络协作完成，没有单一总控节点。

- **误区 3**：一条消息必须整体走同一条路  
  **纠正**：消息常被拆成多个 `packet`，不同包可以走不同路径。

- **误区 4**：分层就是要背名字  
  **纠正**：分层首先是职责分工，层名只是对职责的整理。

- **误区 5**：更大的网络一定会崩掉  
  **纠正**：开放协议、分包、路由和冗余共同支持互联网扩展。

---

## 🧩 教学难点

- 学生容易把“层”理解成固定流水线，而不是抽象边界
- 学生容易看到包在飞，却不知道哪一步是谁在负责
- 学生可能会误把协议名词当作记忆任务，而忽略其协作意义
- `bandwidth` 和 `scalability` 容易被讲成孤立定义，脱离系统设计

## 🎬 场景设计

### 场景 1：Internet vs Web

- **核心问题**：打开网页、发消息、看视频，这些事情依赖的是同一个东西吗？
- **画面设计**：
  - 同屏显示网页、聊天、视频、邮件四张活动卡
  - 下层是一条共享的 `Internet` 基础轨道
  - `Web` 卡片只覆盖其中一部分活动
- **教师讲稿**：
  - “Internet 是基础网络，Web 是跑在上面的一种服务。”
  - “所以今天我们不只是在讲网页，而是在讲这些服务为什么都能工作。”
- **一句话总结**：
  - `Web uses the Internet, but is not the whole Internet.`

### 场景 2：打开一个网页时，谁在负责什么

- **核心问题**：点击一个网页链接后，到底是谁在工作？
- **主视觉原则**：
  - 这一幕不用长比喻，直接展示真实过程动画
  - 屏幕右侧固定四张职责卡：
    - 我要什么
    - 按什么规则交流
    - 往哪条路走
    - 怎样真正发送与接收
- **推荐步骤**：
  1. 浏览器静止，学生点击链接
  2. 顶部出现任务卡：`我要一个网页`
  3. 请求卡片被格式化，显示：`Protocol：规定怎么说`
  4. 请求被拆成多个 `packet`
  5. 包进入网络路径
  6. 服务器返回响应
  7. 响应包重新组合
  8. 页面内容按块填充
- **教师讲稿**：
  - “不要先背层名，先看这一秒是谁在做事。”
  - “我们看到的是同一个任务，被拆成了不同职责。”
  - “网页能打开，不是因为一个地方知道一切，而是因为不同职责按规则协作。”
- **一句话总结**：
  - 分层先是职责分工，后才是术语命名。

### 场景 3：Protocol + Packet

- **核心问题**：为什么消息不会整块飞过去？
- **画面设计**：
  - 一条消息或一个网页片段被拆成多个 `packet`
  - 每个包显示编号
  - 旁边有协议规则卡，标注“必须按同样格式交流”
- **教师讲稿**：
  - “如果没有共享规则，不同系统无法合作。”
  - “如果不分包，传输和补发都会更困难。”
  - “协议决定怎么说，packet 决定怎么分。”
- **一句话总结**：
  - `Protocol` 让大家说同一种话，`packet` 让数据更容易运输。

### 场景 4：Routing + Fault Tolerance

- **核心问题**：为什么断一条路不等于全网瘫痪？
- **画面设计**：
  - 初始多个包走主路径
  - 教师点击使某条链路或节点失效
  - 剩余包自动改道，最终在终点成功重组
- **教师讲稿**：
  - “不同 packet 不一定走同一条路。”
  - “冗余不是浪费，而是可靠性的成本。”
  - “互联网的稳，不来自中央控制，而来自分布式路径。”
- **一句话总结**：
  - 路由和冗余共同构成容错。

### 场景 5：Bandwidth + Scalability

- **核心问题**：为什么互联网能承受越来越多的设备和流量？
- **画面设计**：
  - 对比窄数据通道和宽数据通道，显示同一时间可通过的数据量不同
  - 逐步增加设备或用户数量，系统仍通过分包和多路径继续运行
- **教师讲稿**：
  - “`Bandwidth` 关心的是一次能流过多少数据。”
  - “`Scalability` 关心的是设备和流量增长后，系统还能不能继续工作。”
  - “开放协议和分布式路径，让互联网可以不断扩展。”
- **一句话总结**：
  - 好的网络设计不只要能工作，还要能扩展。

### 场景 6：简化分层与迁移检查

- **核心问题**：前面看到的职责，如何整理成简化层图？
- **展示顺序**：
  - 先显示四张职责卡
  - 再翻转成简化层名：
    - `Application`
    - `Transport`
    - `Internet`
    - `Link / Physical`
- **教师讲稿**：
  - “我们现在才给这些职责命名。”
  - “你不需要背完整模型，更重要的是知道每层负责什么。”
  - “如果换一个应用，底下网络不一定要重写，这就是分层的价值。”
- **迁移检查问题**：
  - 如果网页打不开，可能是哪一层的问题？
  - 如果某条路径断了，为什么系统还可能继续工作？
  - 如果更多设备接入 Internet，为什么系统仍能扩展？
- **一句话总结**：
  - 层图是帮助理解职责的工具，不是记忆比赛。

## 🧠 本章金句

- **The Internet works without a central boss.**
- **Packets travel separately, then get reassembled.**
- **Protocols let independent systems cooperate.**
- **Layering is about responsibilities, not memorization.**
- **A strong network design must scale as well as function.**
